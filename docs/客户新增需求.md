## 1. 【变更】难度解锁条件：连续 2 次达标 → 达标 1 次

**客户原话**：「任务模拟是允许新人反复做的，当新人对于会话的适应度已经达到需求（达标 1 次）后就解锁下一章节。」

**现状**

- 解锁进度在每次接待结束时累加（`reception.service.ts` 的 `updateUnlock`，由 `finalizeAttempt` 调用），
  **任务训练与自由练习都计入** —— 也就是说「靠任务训到达标来解锁下一档」这条链路本来就是通的。
- 但阈值参数 `unlockConsecutive` 默认是 **2**，而且**中途失败会把连续计数清零**。

**改动点**

| 位置 | 改什么 |
| --- | --- |
| `backend/src/domain/types.ts` | `DEFAULT_PARAMS.unlockConsecutive`：`2` → `1`（阈值 1 时「连续」约束自然失效，`updateUnlock` 逻辑不用动） |
| `frontend/src/pages/Settings.tsx` | 「难度解锁条件」的说明文案（现在写的是「连续 2 次达标」） |
| `backend/test/domain/params.spec.ts` | 断言默认参数值的用例跟着改 |
| `tools/acceptance-manifest.mjs` | 方案 10.3 默认参数表写的是 **2 次**，改完后会与方案不一致 —— 给审计加「客户覆盖值」机制，**把偏差显式登记**，而不是让看板长期报「参数与方案不一致」 |
| `README.md` / `_handoff/PROJECT_HANDOFF.md` | 各记一句变更 |

**已确认（2026-10-02）**：「章节」= **难度档位**（L1 → L2 → L3 → L4）。
即：在某一档达标 1 次，即解锁下一档。不是任务序列机制。

**验收方式**：用客服账号做一次任务训练并达标 → 结束后查 `/api/receptions/levels`，下一档应变为 `unlocked: true`。

**补充规则（按现状保留）**

- 解锁进度只在「达标」时前进，未达标时连续计数清零；阈值改为 1 后，等价于「一次达标即解锁」。
- 已解锁的档位**不回退**。
- 任务训练与自由练习都计入解锁进度（现状即如此）。

## 2. 【新增】客服不开放自由练习，入口只留管理员/主管

**背景**：客服在使用中反馈「《我的任务》和《在线模拟接待》功能重复」——同一个接待引擎被摆成了两个平级入口。
经确认，**客服只做任务训练**，自由练习只给带教/管理员。

**只改菜单是不够的**，需要 4 处一起改：

| # | 位置 | 改动 | 为什么必须改 |
| --- | --- | --- | --- |
| 1 | `frontend/src/layouts/AppLayout.tsx` | 「在线模拟接待」（自由练习）菜单项只对 admin/leader 显示；客服的训练中心保留「我的训练 / 我的任务 / 模拟接待明细」 | 表层入口 |
| 2 | `frontend/src/pages/Reception.tsx` | 客服且**无 `taskId`/`attemptId`** 时，不渲染自由练习难度卡片，改为引导 + 跳转《我的任务》 | 客服可能翻到旧链接（收藏夹 / 历史记录） |
| 3 | `frontend/src/pages/Dashboard.tsx` | 首页「快速开始」难度卡对客服隐藏（`startReception` 调的就是 `source:'free'`） | **最容易漏的一处** |
| 4 | `backend/src/modules/reception/reception.service.ts` | `start()` 中：`source === 'free'` 且角色为 `agent` → 抛 **1003**「客服暂未开放自由练习，请从任务训练进入」。需把 `AuthUser` 传进 `start()`（现在只传了 `accountId`） | **关键**：否则客服直接调接口或走旧链接仍能开局 |

**顺带**：管理员/主管进 `/reception` 时标题补一个「自由练习」标签，与「任务训练：xxx」形成对称，
这是「重复感」的一半来源。

**要补的用例**

1. 客服 `POST /api/receptions {source:'free'}` → **1003**
2. 管理员同样调用 → **0**
3. 主管同样调用 → **0**
4. 客服带 `taskId`（`source:'task'`）→ **0**（任务训练不能受牵连）

**验收口径要跟着改**：方案 9.1 的「四档难度可开局且并发数正确」，
以后要用**管理员账号**验（客服已不能自由开局）。

## 3. 【新增】管理账号可设置并发接待人数（1–4 保留）

**客户原话**：「在线模拟接待 我需要管理账号能够设置总回复人数，1-4 并发保留」

**现状**

- 系统参数页已有「并发接待上限」（`maxConcurrent`，后端校验 1–4）。
- 开局取 `min(难度档位的并发数, 并发接待上限)` —— 也就是**只能往下压，不能往上抬**：
  设成 2，L4 只接 2 个买家，但 L1 永远还是 1 个。

**三种可选口径**

| 口径 | 行为 | 预估 |
| --- | --- | --- |
| ① **每档可配**（推荐） | 系统参数里给 L1–L4 各配一个「接入人数」，默认仍是 1/2/3/4，可改成 1–4 内任意值 | 1.5–2.5h |
| ② 开局时临时指定 | 开始接待时直接选「本次接入 N 人」（1–4），管理员/带教可见，客服沿用难度默认 | 2–3h |
| ③ 全局一个数 | 所有难度都用同一个接入人数，难度只影响风格与轮数 | 1–1.5h |

**推荐 ①** 的原因：管理员能自由设人数，同时**默认值保持方案的 1/2/3/4**，
方案 9.1「四档难度可并发数正确」的验收口径不会被破坏；且能与现有「并发接待上限」自然叠加。

**已确认（2026-10-02）：按口径 ① 实现。** 具体规则：

| 项 | 规则 |
| --- | --- |
| 新增参数 | `levelConcurrent: { L1, L2, L3, L4 }`，默认 **1 / 2 / 3 / 4**（与方案一致，向后兼容） |
| 取值范围 | 每档 1–4，越界拒绝并提示 |
| 与现有上限的关系 | 实际接入人数 = `min(levelConcurrent[档位], maxConcurrent)`；全局上限保留 |
| 难度名称 | **不动**（仍叫「话术适应 / 简单 / 进阶 / 困难」），人数只在参数里体现 |
| 生效范围 | 自由练习与任务训练**都**按该参数取人数 |

**默认值不变**意味着：不改参数时，系统行为与现在完全一致，方案 9.1 的验收口径不受影响。

## 8. 【新增】各档位可设「本次模拟总接待人数」（C5，2026-10-02 第二轮确认）

**需求**：各档位除了「同时在线接入人数」，还要能设「本次模拟一共接待多少人」。

**口径**：

1. 默认等于该档接入人数（1/2/3/4）；**不配置时行为与改造前完全一致**。

## 9. 【新增】无效 / 敷衍回复判定 + 实时预警（C6，2026-10-02 第二轮确认）

**需求**：管理员可配置「哪些回复算无效/敷衍」，命中时当场提醒客服并打标，明细可复盘。

**可配置项**（系统参数页 →「无效 / 敷衍回复判定」，**总开关默认关**）：

| 配置 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| 总开关 | 关 | 开/关 | 关闭时完全按改造前行为 |
| 重复判定方式 | 连续 N 次完全相同 | 连续 N 次 / 与上一条完全相同 | 对应官方「与上一轮完全相同」「连续多条完全相同」 |
| 连续次数阈值 | 3 | 2～10 | 同一内容连续出现 N 次即判无效 |
| 未解决判定 | 关 | 开/关 | 连续 N 轮命中要点为 0 |
| 连续未命中轮数 | 3 | 2～10 | **近似**官方「买家明确要求后仍未改善」 |
| 敷衍词表 | 空 | 自由维护 | **业务方自定义，非平台官方口径** |

**重要边界**：官方只公布了三种敷衍情形并声明「以系统判定为准」，**没有公开词表**；
本系统的词表属自定义口径，界面已标注。词表与 `forbiddenWords`（禁用词库）**分开维护**，
避免同一句被「话术扣分 + 情绪上升 + 600 秒」三重惩罚。

**联动**：被判无效的回复不参与响应时长计算——该轮时长回退到「首条有效回复」，
始终没有有效回复则按官方口径记 600 秒（见 `docs/方案源稿.md` 4.2 节）。

**判定落点**：`backend/src/domain/reply-validity.ts`（纯函数，入参 messages + questions + params，
出参每轮的有效/无效回复序号）；规则随开局写进 `param_snapshot`，历史接待按旧快照复算。

**验收**：`backend/test/domain/reply-validity.spec.ts`（7 条）+

## 14. 【变更】补位口径 = 空位即补；接待买家 = 累计已进线（C11，2026-10-03 按赤兔火眼实测对齐）

**背景**：第 10 节曾按「正在接待的人全部回复结束后重新生成新一轮」把补位改成**整批换新**。
客户随后让我实际跑完一场赤兔火眼的自由练习去核对，实测结论与整批换新**不一致**，于是按实测口径改回。

**赤兔火眼实测（完整一场：10 个买家 / 最多同时 3 个，详见 `docs/赤兔火眼补位规则观察.md`）**：

1. 左栏只有 `接待买家 / 正在接待 / 已结束 / 转交`，且全程 `接待买家 = 正在接待 + 已结束 + 转交`
   → **接待买家是累计已进线**，不含还没进线的；界面上**没有**排队名单。
2. **补位是空位即补**：任意一个买家结束（买家自己结束，或客服点会话头部 ✕ 主动结束），
   空出的名额在**几秒内**被下一个买家补上（实测新买家进线时等待时长只有 1～6 秒）。
3. 名额用满即停：累计进线到 10 之后，再结束会话也不再进新人。

**改动**：

- `reception.service.ts` 的 `promoteWaiting()` 去掉「还有人在接待就不补」的判断，改为按空位补满
  （`slots = 同时在线上限 - 正在接待`）；新买家进线前留 **1.5～4.5 秒**再推第一条问题，
  对齐赤兔实测的「几秒内进线」。
- 去掉上一版为此引入的「轮次」概念（`sessions.round_no` 列与队列上的 `第N轮` 标签）。
- 接待页左栏「接待买家」由「本次总接待人数（含排队）」改为 **`已进线数 = 总人数 - 待接入数`**；
  「剩余会话（待接入）」与「待接入」页签保留（我们的排队是真实存在的，只是不计入接待买家）。

**验收**：

- `client-requirements.e2e-spec.ts#C5：总接待人数大于同时在线时，多出的买家排队，空位即补（对齐赤兔火眼）`

## 17. 【新增】推送问题按比例混合售前 / 售后（C14，2026-10-03）

**客户原话**：「弹出的问题我需要增加设定，分为售前/售后两方面，目前的模拟回复默认为售前的内容，

**口径**：

| 类别 | 含义 | 问题长什么样 |
| --- | --- | --- |
| **售前**（大部分） | **还没有订单**，只咨询商品信息 | 面料/颜色/尺码/评价/优惠/多久能到…… |
| **售后**（小部分） | **买完商品后**的订单类咨询 | 改收货地址 / 改快递 / 催发货 / 改单 / 改电话 / 备注配送 / 退换 / 物流 |

**新参数**（系统参数 →「问题构成（售前 / 售后）」）：

| 参数 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| 售后问题占比（%） | **20** | 0～80 | 一次接待里约这个比例的问题会被换成「买完商品后」的订单类问题；填 0 = 整场都是剧本本身的话题 |

**实现**：

- `domain/question-seq.ts` 新增 `mixQuestionSeq()`：保留剧本本身的话题作为主体（**开场的问题不动**），
  把**靠后的约 N% 轮次**替换成另一阶段的题库，并重新计算这些轮次的 `stage` 与 `orderStage`；
  「小部分」有硬上限——最多换掉一半。
- 题库放在 `db/seed-content.ts`：`ORDER_AFTERSALE_QUESTIONS`（买完商品后的订单类，6 条）、
  `PRESALE_PRODUCT_QUESTIONS`（纯商品咨询，6 条）；同一局里按会话序号错开取题，避免每个买家都问同一句。
- 售前剧本混售后问题，**售后剧本反向混售前问题**，两个方向都保证「大部分仍是剧本本身的话题」。
- **订单卡片跟着问题走**，并顺带细化售后口径（对应三张参考图）：
  催发货 / 改地址 / 改快递 / 改单这类**还没发货**的 → 「待发货」；物流 / 签收 / 退换 / 质量这类**已经发出**的 → 「已发货」。
  售前里问到发货/时效的仍是「待发货」，其余售前是「待支付」。

**实测样例**（开局后第一个会话，比例 20%、6 轮）：

```
1.[售前]容易皱吗？ → 待支付
2.[售前]需要经常熨烫吗？ → 待支付
3.[售前]出差带着方便吗？ → 待支付
4.[售前]那大概多久能处理好呢？ → 待发货
5.[售前]我再看一下别家，你们有什么优势吗？ → 待支付
6.[售后]收货人电话写错了，帮我改一下电话吧 → 待发货   ← 买完商品后的订单类问题
```

**验收**：

- `backend/test/domain/question-seq.spec.ts`（3 条：按比例替换靠后轮次 + 序号连续、比例 0 不混 / 上限一半、售后剧本反向混售前）；
- `backend/test/domain/order.spec.ts`（售后里「还没发货」的订单类问题配待发货，已经发出的才配已发货）；
- `client-requirements.e2e-spec.ts#C14：售前 / 售后问题按比例混合，比例可配（默认两成售后）`——

## 19. 【新增】下发任务时「剧本 + 商品」可同时多选（C16，2026-10-03）

**客户原话**：「我指的是在设置回复接待任务的时候剧本和商品能够多选。」

### 19.1 任务范围新增一档：指定剧本 + 商品（都能多选）

原来「剧本范围」是**互斥的单条件**：按剧本分类 / 按关联商品 / 按商品种类 / 指定剧本清单——
选商品就不能选剧本，选剧本就不能选商品。现在新增 **「指定剧本 + 商品（都能多选）」**：

| 选择 | 结果 |
| --- | --- |
| 剧本 A、B + 商品 P1、P2 | 只抽「A/B 里、关联了 P1 或 P2」的剧本 |
| 只选剧本（商品留空） | 等价于「指定剧本清单」 |
| 只选商品（剧本留空） | 等价于「按关联商品」 |
| 两个都不选 | 不限制 |

界面上两个框都是多选、都带搜索，商品后面括注分类，方便带教一眼看清选的是哪个品类的货。
组合不可能满足时（例如「剧本 A + A 没关联的商品」），开局会明确提示
「任务限定的「剧本 + 商品」组合下没有可用剧本，请让带教调整任务范围」。

### 19.2 顺带把《客户问题剧本》的商品口径说清楚

批量生成的组合口径**没有变**（仍是「买家咨询背景 × 买家咨询内容」），变化的是商品怎么分配：

- **每条内容只在「与它兼容的已选商品」里按序轮转**（例如内容是「鞋码」就只用所选的鞋靴商品）；
  配不到兼容商品的内容会被**跳过**，接口返回 `skipped` 原因，页面会提示
  「有 N 条咨询内容因「商品与问题不匹配」被跳过：xxx（原因）」。
- 单个创建时不匹配**直接报错**（更适合"立刻指出哪里不对"）：
  「商品与咨询内容不匹配：问题「…」不适合商品分类「…」，请调整关联商品或换一条咨询内容」。

这样多选商品是真实生效的，同时不会造出「问题与商品不一致」的剧本（沿用 C15 的品类一致性规则）。

**验收**：

- `task-scope.spec.ts`（剧本 + 商品同时多选：两个条件都命中才放行、单侧留空等于只用另一侧、两侧都空 = 不限制）；
- `client-requirements.e2e-spec.ts#C16`——用「剧本 A + A 的商品」下发能抽到该商品，
  用「剧本 A + 别的商品」下发会返回明确提示（不会随便抽一个别的剧本/商品）。

## 20. 【修正】右栏「商品」页签改放《商品库》的商品（2026-10-03）

**客户原话**：「订单当中的咨询宝贝没有问题，但是商品页面里面不应存在咨询宝贝，
商品页面里面应该商品库的商品。」

**改前**：右栏两个页签都是「咨询宝贝」——「订单」页签顶部一块、「商品」页签整页都是当前会话的那件商品。

**改后**：

| 页签 | 内容 |
| --- | --- |
| **订单** | 顶部「咨询宝贝」（当前会话咨询的那件商品 + 邀请下单 / 计算价格 / 规格属性 / 商品视频）→ 订单状态页签 → 订单卡。**保持不动** |
| **商品** | **《商品库》的商品列表**：顶部「商品库 · 共 N 件」+ 关键词搜索（商品名称/商品ID）+ 分类筛选；列表每条显示缩略图、标题、`分类 · 商品ID`、价格与库存，操作是「**发送卡片**」（把该商品的商品卡片插进输入框）与「**规格属性**」（弹出该商品在商品库里的真实属性） |

**顺带修掉的一个隐患**：从「商品」页签发**别的商品**时，对话里的商品卡原来是按"当前会话的商品"渲染的
（图/价格/服务承诺会串）。现在商品卡会按消息内容里的 **商品ID 去商品库取那件商品**，
取不到才回落到会话商品——发的哪件就显示哪件。

**另外**：对话区商品卡上的占位按钮「…」去掉了（按钮行改为「计算价格 / 邀请下单 / 规格/属性」一行放得下）。

**验收**：`npm run render:check -- --shots=<目录>` 的截图清单新增 `03d-接待页-商品页签`，
与 `03c-接待页-订单页签` 一起人工核对（订单页签仍有咨询宝贝、商品页签是商品库列表）。
