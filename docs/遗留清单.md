## 6. 与方案清单的形态差异：6 处（有意，不是漏做）

| 方案写法 | 本版实现 | 原因 |
| --- | --- | --- |
| `DELETE /api/accounts` | 停用：`PUT /api/accounts/:id { status: 0 }` | 方案 3.8 F8-02 只要求「停用」；账号不做物理删除，历史接待可追溯 |
| `DELETE /api/backgrounds` | `POST /api/backgrounds/batch-delete` | 统一走批量删除，且被剧本引用时返回 3001 而不是静默删掉 |
| `DELETE /api/contents` | `POST /api/contents/batch-delete` | 同上 |
| `PUT /api/categories` | `PUT /api/categories/:id`（改名，级联更新引用）+ `PUT /api/categories/reorder`（排序） | 分类的「改」实际只有改名与排序两件事，拆成两个更明确的动作 |
| `POST /api/scripts/batch-generate/async` | 同一个 `/api/scripts/batch-generate`，超过 `batchAsyncThreshold` 自动转异步 | 前端不需要区分两个入口；进度与取消在 `/api/scripts/batch-generate/tasks/:id` |
| `PUT /api/tasks` | 未实现（任务属二期） | 本版只做了创建、列表、报表、删除 |
| `POST /api/cases/:id/to-script` | `POST /api/cases/:id/to-content` | 案例先沉淀成「买家咨询内容」，再由《客户问题剧本》批量生成剧本；与方案 3.5 的两条路径等效，且内容可复用 |
