# 迁移指南：CloudBase（云开发）→ 腾讯云轻量服务器（低延迟优化）

> 适用对象：当前「CloudBase 静态托管前端 + 云托管跑后端 + Supabase 外部 PostgreSQL」的部署，
> 目标是把**整套系统**搬到腾讯云 Ubuntu 轻量服务器上，消除明显延迟。
> 本目录（`deploy/lighthouse/`）是迁移所需的全部新文件，仓库原有文件一律未动。

## 0. 为什么现在慢（迁移后为什么快）

| 环节 | 现状 | 搬到轻量服务器后 |
| --- | --- | --- |
| 数据库 | Supabase 免费版，境外区域；每个 API 请求要串行执行多条 SQL，每条都承担 **100~300ms 跨洲/跨境往返** —— 这是延迟大头 | PostgreSQL 就在同一台机器上，容器间 RTT **< 1ms** |
| 后端 | CloudBase 云托管体验版，**0.25~0.5 核**共享 CPU，无人访问时冷启动要数秒 | 轻量服务器整核独享，常驻内存，无冷启动 |
| 上传文件 | 云托管无持久卷，图片重启即丢 | `uploads` 数据卷持久化，且每日随库一起备份 |
| 前端静态资源 | CloudBase CDN（这点挺好） | 同机 nginx 提供 + **gzip + hash 文件 30 天强缓存**（1.4MB 主包压到约 400KB） |

预期效果：普通接口从「秒级」回到「几十毫秒」；登录、列表、开局等操作不再转圈。

## 1. 动手前确认三件事

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| 轻量服务器在哪个地域？ | 大陆地域的 80/443 端口需要域名 **ICP 备案** 才放得通 | 本方案默认走 **`http://IP:8080`，不需要备案**；若想要域名 + HTTPS（见 §6 可选进阶），大陆机先备案，境外机直接办 |
| 服务器配置？ | 2 核 2G 够跑（本方案的 compose 就是按 2G 调优的）；4G 以上更从容 | 2G 已验证可跑：PG(约 300MB) + API(约 300MB) + nginx/web(约 50MB) |
| 现在线上有没有要保留的数据？ | 有 → 需要 §5 的 Supabase 数据迁移；没有 → 跳过 §5，全新 seed | 训练记录、改过口令的账号都在 Supabase 里 |

## 2. 初始化服务器（二选一）

### 方式 A：一键脚本（推荐）

先把本目录的改动提交并 push 到 GitHub，然后 SSH 上服务器执行：

```bash
sudo bash deploy/lighthouse/setup-server.sh
```

脚本会自动：装 Docker → 防火墙放行 8080 → 克隆仓库到 `/opt/cs-training` → 调 `up.sh` 完成部署。

> 别忘了**腾讯云控制台 → 轻量服务器 → 防火墙 → 添加规则放行 TCP 8080**（控制台这道防火墙脚本碰不到）。

### 方式 B：手动

```bash
# 1. 装 docker（Ubuntu）
curl -fsSL https://get.docker.com | sh
# 2. 放通端口
sudo ufw allow 8080/tcp
# 3. 拉代码 + 部署
git clone https://github.com/Maiduo-Alt/maiduo123.git /opt/cs-training
cd /opt/cs-training
bash deploy/lighthouse/up.sh
```

首次构建约 3~8 分钟（拉基础镜像 + npm 依赖）。完成后脚本会打印访问地址，健康检查应返回
`{"code":0,...,"data":{"status":"ok","db":"up","memoryDb":false,...}}`。

## 3. 迁移 Supabase 数据（线上有数据才需要）

在服务器项目根目录执行（连接串用 Supabase **连接池**地址，见 `deploy/CLOUDBASE.md` 的排坑表）：

```bash
bash deploy/lighthouse/migrate-from-supabase.sh \
  'postgresql://postgres.<ref>:<密码>@aws-0-<region>.pooler.supabase.com:5432/postgres?sslmode=require'
```

过程：导出 → 短暂停 api（几十秒内）→ 灌入本地库（`--clean --if-exists`，可重复执行）→ 重启自检。
迁移后请抽查：老账号能否登录、《明细》历史记录是否齐全。

> ⚠️ 商品图/头像等**上传文件不在数据库里**，而云托管没有持久卷——此前重启就可能已经丢了，
> 这部分只能在迁移后重新上传。新服务器的 `uploads` 卷是持久的，之后不会再丢。

## 4. 验收（切流前必做）

| 项 | 怎么验 |
| --- | --- |
| 健康检查 | 浏览器/终端访问 `http://<服务器IP>:8080/api/health`，`memoryDb` 必须是 `false` |
| 登录 | `admin/Admin@123` 登录成功（迁移过数据则用改后的口令） |
| 实时通道 | 进《在线模拟接待》开局，买家消息**秒推**、倒计时每秒跳动（这就是原来最卡的地方） |
| 完整链路 | 随便打一局：进线 → 回复 → 结束 → 《明细》出现记录 → 复盘可见 |
| 并发 | 开两个浏览器分别用 admin/agent 登录同时训练，互不掉线 |

## 5. 切流：前端放哪

### 方案 A（推荐）：前端也搬到服务器，单入口 `http://IP:8080`

仓库 compose 已经包含 `web`（前端构建 + nginx 托管），§2 部署完即就绪。
前端调 API 走同域，无跨域、无混合内容问题，WebSocket 也同源。内部培训系统用这个最省事。

### 方案 B：前端继续留在 CloudBase 静态托管（只搬后端）

**前提：服务器上必须有 HTTPS 的 API 地址**——CloudBase 站点是 HTTPS 的，浏览器会拦截
HTTP 接口（混合内容）。需要：一个域名解析到服务器 IP + 免费证书（Let's Encrypt）。
另外大陆机房域名要备案，境外机房不用。做法：

```bash
cd frontend
VITE_API_BASE=https://api.<你的域名> VITE_SOCKET_URL=https://api.<你的域名> npm run build
# 把 dist 传回 CloudBase 静态托管
```

服务器侧再用 nginx/certbot 终结 443 反代到 api:3000（需要的话我可以补这份配置）。

> 对培训场景，方案 A 的访问速度已经足够（首屏 gzip 后约 400KB）；方案 B 适合学员分布广、
>  want 静态资源走 CDN 的情况。

## 6. 切流后与回滚

1. **保留 CloudBase 一周**：先别停云托管服务，观察新地址稳定后再停（停止云托管即不再按量计费）；
2. Supabase 项目可降级/暂停，保留作冷备份（里面还有迁移前的快照）；
3. **回滚**：把前端改回指向云托管地址重新构建上传即可，数据库两边在观察期内都是完整的；
4. 把服务器 `.env` 里的 `JWT_SECRET` 备份好；如果沿用 CloudBase 上原值，已登录用户切流时无感；
   用新随机值则所有人需要重新登录一次。

## 7. 日常运维速查（都在服务器 `/opt/cs-training` 下）

| 事情 | 命令 |
| --- | --- |
| 看状态 | `docker compose -f deploy/lighthouse/docker-compose.yml --env-file .env ps` |
| 看日志 | `docker compose ... logs -f --tail=200 api` |
| 升级代码 | `git pull && bash deploy/lighthouse/up.sh` |
| 手动备份 | `docker compose ... exec backup sh -c 'pg_dump --format=custom --no-owner --file /backups/manual.dump "$DATABASE_URL"'` |
| 恢复备份 | `docker compose ... stop api && docker compose ... exec -T postgres pg_restore --clean --no-owner -U cs_training -d cs_training < backups/<文件>.dump && docker compose ... up -d api` |
| 磁盘占用 | `docker system df`；备份在 `./backups`（保留 30 份自动清理） |

## 8. 自测延迟对比（迁移前后各测一次）

```bash
# 测首字节时间（登录接口，需先手动调 /api/auth/login 拿 token 的 URL 换成健康检查也行）
curl -o /dev/null -s -w '总耗时 %{time_total}s / 首字节 %{time_starttransfer}s\n' \
  https://cs-training-web-huihuamoni-d6gm8a2lbc70ac21a.webapps.tcloudbase.com/api/health
curl -o /dev/null -s -w '总耗时 %{time_total}s / 首字节 %{time_starttransfer}s\n' \
  http://<服务器IP>:8080/api/health
```

典型结果：CloudBase 链路 0.5~2s（含跨区 SQL 往返），本机链路 0.01~0.05s。
