# 在线模拟接待训练系统

面向新入职在线客服的并发接待模拟训练平台（PC Web）。系统以抖店客服工作台为界面与计时蓝本，覆盖"素材 → 剧本 → 接待 → 评分 → 明细 → 复盘"的完整训练闭环。

需求与实现方案文档见 [`在线模拟接待训练系统_需求与实现方案_v1.0.docx`](在线模拟接待训练系统_需求与实现方案_v1.0.docx)，可维护源稿见 [`docs/方案源稿.md`](docs/方案源稿.md)。

## 一、技术组成

| 层次 | 实现 |
| --- | --- |
| 前端 | React 18 + TypeScript + Ant Design 5 + Vite（`frontend/`） |
| 后端 | NestJS 10 + TypeScript + node-postgres（`backend/`） |
| 数据库 | PostgreSQL 15（生产）；本机开发可用内存数据库模式（pg-mem） |
| 实时通道 | Socket.IO（`/realtime`），推送买家消息、计时同步、超时提醒、会话结束 |
| 部署 | Docker Compose（nginx + web + api + postgres + redis + backup） |

## 二、八大功能模块与代码对应

| 模块 | 前端页面 | 后端模块 |
| --- | --- | --- |
| 在线模拟接待 | `frontend/src/pages/Reception.tsx` | `backend/src/modules/reception/` |
| 模拟接待明细 | `Records.tsx`、`RecordDetail.tsx` | `modules/records/` |
| 客户问题剧本 | `Backgrounds.tsx`（素材库）、`Scripts.tsx`（剧本） | `modules/materials/`、`modules/scripts/` |
| 商品库 | `Products.tsx` | `modules/products/` |
| 案例收藏 | `Cases.tsx` | `modules/cases/` |
| 回复模拟任务 | `Tasks.tsx` | `modules/tasks/` |
| 沟通风格 | `Styles.tsx` | `modules/styles/` |
| 账号 | `Accounts.tsx`、`Settings.tsx` | `modules/accounts/`、`modules/settings/`、`modules/auth/` |

核心业务规则（计时、评分、抽取、情绪、风格占比、难度解锁）集中在 `backend/src/domain/`，为纯函数实现，可脱离框架单测。

## 三、快速启动

```powershell
# 1. 安装依赖（首次）
npm install

# 2. 编译后端
npm run build -w backend

# 3. 启动 API（内存数据库模式，开箱即用，无需安装 PostgreSQL）
npm run dev:api:mem

# 4. 另开一个终端启动前端
npm run dev:web        # 访问 http://localhost:5173
```

演示账号：管理员 `admin / Admin@123`，带教 `leader / Leader@123`，客服 `agent / Agent@123`。

### 使用真实 PostgreSQL

```powershell
# backend/.env
DATABASE_URL=postgres://user:password@127.0.0.1:5432/cs_training

npm run migrate     # 建表
npm run seed        # 初始化角色、账号、风格、商品、素材与剧本

```

### 部署到内网服务器（Docker Compose 单机）

> 现状说明：**本机验收跑的是内存库模式**（数据在进程内存里，重启即清空，需要用 `npm run demo:data` 重新铺）；
> 生产/内网部署用的是下面这套 Docker Compose，产物已随仓库提供，但需要一台装了 Docker 的机器。
> 另外方案第 9 节的「部署路线 A/B/C」还没拍板——注意云开发免费体验版不提供 PostgreSQL 与 Redis。

```bash
# 在仓库根目录（需要放行 docker 的网络下载镜像）
bash deploy/up.sh                 # 一键：生成 .env（随机 JWT_SECRET）→ 构建 → 启动 → 等健康检查
# 等价的手动步骤：cp deploy/env.production.example .env && docker compose up -d --build
# 打开 http://<服务器IP>:8080

docker compose ps                 # 看各服务状态
docker compose logs -f api worker # 看 API / 后台任务日志
curl http://127.0.0.1:8080/api/health   # 健康检查（memoryDb 必须是 false）
docker compose down               # 停（数据卷 pgdata/uploads 保留）
```

| 组成 | 说明 |
| --- | --- |
| `postgres:15-alpine` | 业务库；卷 `pgdata` |
| `redis:7-alpine` | 实时调度的延迟队列（配了 `REDIS_URL` 自动启用；不配则用进程内实现） |
| `api` | `backend/Dockerfile` 构建；启动时按顺序执行 `migrate → seed → main`，端口 3000（仅内网） |
| `worker` | 复用 api 镜像、`WORKER_ONLY=true`：只跑延迟队列 / 超时检测 / 异步导入，不接 HTTP（方案 5.10） |
| `web` | `frontend/Dockerfile` 构建（多阶段：npm 构建 → nginx 托管静态资源） |
| `nginx` | 对外端口 **8080**；反代 `/api/`、`/realtime/`（WebSocket）、`/uploads/` 与前端 |
| `backup` | 每天 `pg_dump` 到宿主机 `./backups`，只保留最近 30 份（方案 5.10） |

**上线材料**：`deploy/ONLINE.md`（上线清单：机器规格、端口、验收、日常运维、备份恢复、HTTPS）；
`deploy/up.sh`（一键部署）；`node tools/make-release.mjs` 打一个不含 node_modules 的上线包（`release/*.zip`，服务器上解压执行 `bash deploy/up.sh`）。

**只想零成本先跑起来**：见 `deploy/FREE.md`（三套免费方案）——
推荐 **Supabase 免费 Postgres + Render 免费 Web Service（仓库里有 `render.yaml`）+ Cloudflare Pages 免费静态托管**；
若有一台永久免费小机（如 Oracle Always Free），直接用 `deploy/up.sh` 或
`deploy/compose.managed-db.yml`（库走托管、机器只跑 api/worker/web/nginx）。
前端已支持 `VITE_API_BASE` / `VITE_SOCKET_URL`：前后端分开部署时构建一次即可指向外部 API。

**用腾讯云 CloudBase（云开发）+ GitHub 仓库部署**：见 `deploy/CLOUDBASE.md` ——
云托管（CloudBase Run）从 GitHub 构建 `backend/Dockerfile` 跑 API（容器端口 3000、健康检查 `/api/health`、
启动命令里先 `migrate → seed`），前端放静态网站托管，**数据库必须是外部 PostgreSQL**
（CloudBase 自带数据库不是 PG；用 Supabase 免费版或腾讯云 PG）。

部署环境变量（放 `.env`，模板见 `deploy/env.production.example`，compose 会自动读取）：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `JWT_SECRET` | `change-me-in-production`（占位） | **上线必须替换**；`deploy/up.sh` 首次运行会自动生成随机值 |
| `WEB_PORT` | `8080` | 对外端口，被占用时可改 |
| `POSTGRES_PASSWORD` | `cs_training_pwd` | 数据库口令，建议一并改掉 |
| `UPLOAD_DIR` | `/app/uploads`（卷 `uploads`） | 商品图 / 内容配图落盘位置 |
| `USE_PG_MEM` | `false` | 部署时必须是 false（true 才走内存库） |

运维相关的三项已按方案 5.10 落地：**健康检查** `GET /api/health`（见 `backend/src/modules/health/`，api 容器的 healthcheck 也用它）、
**日志轮转**（每个长跑服务的 json-file 驱动保留 30 份）、**每日备份**（backup 容器，30 份上限）。

> 部署配置本身可以离线核对：`npm run deploy:check` —— 逐项检查 compose / Dockerfile / nginx 里引用的
> 文件、npm 脚本、端口、反代上游名是否都对得上（不需要 docker，也不联网）。

## 五、本版实现边界（与方案文档的差异）

1. **案例收藏的平台导出适配器**：方案中列为二期，本版实现文本粘贴导入与"转为咨询内容"，文件导入适配器待取得真实导出样例后实现。
2. **AI 相关**：按一期结论，系统不接入任何模型服务；`RuleEngine` 为确定性实现，买家行为、判定与评分均可复现。
3. **评分阈值**：方案 10.2 的 Q1（抖店考核细则原文）已于 2026-10-02 取得，平均响应已按官方公式实现（轮次加权、未回复记 600 秒、无效回复回退到首条有效回复）。
   官方**没有**公布「≤ N 秒」的合格线，代码里的 `avgResponseLimitSec = 60` 是本项目自填默认值，在《系统参数 → 考核规则》里可改，改完只对新接待生效。
4. 前端首屏包体积约 1.4 MB（Ant Design 全量），如需优化可按路由懒加载与 `manualChunks` 拆分。

已补齐的方案项：

- **实时调度（方案 5.5）**：定时调度抽象为 `SchedulerLike`。默认进程内实现；配置 `REDIS_URL` 后自动切换为 Redis 有序集合延迟队列，多实例部署时同一个延迟任务只会被一个实例执行、周期任务用租约保证单实例运行。
- **服务端计时权威（方案 5.5）**：新增 `timer.tick`（服务端每秒下发各会话已等待/剩余秒数）与 `client.ack`（前端每秒心跳），前端不再自行推算计时。
- **Excel 导入（方案 3.4）**：`.xlsx` 与 CSV 共用同一套表头校验与落库逻辑；解析器用 Node 内置 zlib 实现（`backend/src/common/xlsx.ts`），不引入 SheetJS 等第三方依赖。
- **重启可恢复（方案 5.11 可用性）**：服务重启不再把进行中的接待判为异常中止，而是保持 running 并重新挂载丢失的推送定时器；等待时长始终按数据库里的 `last_buyer_at` 计算，重启后接着计时。
- **操作审计日志（方案 5.11 安全）**：新增全局 `AuditInterceptor`，所有写操作（POST/PUT/PATCH/DELETE）在请求结束后写入 `action_logs`，记录操作人、动作、路径与脱敏后的请求体；密码等敏感字段不入库，超长内容自动截断。
- **手机号脱敏（方案 5.11 安全）**：新增 `common/mask.ts`，`GET /api/accounts` 与个人资料接口统一返回 `138****1234` 形式。
- **图片上传（方案 3.4 / 3.3）**：新增 `POST /api/uploads`（仅管理员/主管，限 5MB、仅 PNG/JPG/WEBP/GIF），图片按静态资源对外提供；商品表单支持上传主图与详情图（详情图此前根本没写库，已修），客户问题内容支持上传配图。上传目录由 `UPLOAD_DIR` 控制，Docker 部署挂载 `uploads` 卷、nginx 代理 `/uploads/`。
- **个人资料与自助改密（方案 3.8 F8-05/F8-06）**：此前后端有接口但没有界面。现右上角头像菜单新增「个人资料」，可改昵称、手机号、头像（头像存 `preference.avatarUrl`，不动表结构）并自助修改密码。
- **超时提示音与队列排序（方案 3.1 F1-04/F1-10）**：接待页接近超时/已超时除变色外增加提示音（Web Audio 合成，无需音频资源）；左侧会话队列支持按剩余时间或对话进度排序，并可分组展示。
- **接待页严格对齐参考图 1（方案 3.1.5 / 参考图 1）**：三栏通铺白底 + 1px 分隔线（不再是留间距的圆角卡片）。顶部为模拟客户端标题栏（淡蓝底 + 白底页签 + 加号），难度 / 剩余会话数 / 接待已用时长 / 任务名称 / 编号移入标题栏右侧。左栏为 2×2 概览数字与右上展开箭头、圆角搜索框、`正在接待 / 接待结束` 页签、「列表设置」排序分组栏，列表项含序号徽标、未读红点、咨询商品标签与计时（超 30 秒橙色、超 180 秒红色）。中栏为序号徽标 + 买家昵称 + 复制昵称 + 「添加备注」入口、醒目倒计时与「更多」菜单（插入商品卡片 / 转交 / 结束会话 / 结束本次接待）；对话区首条为买家进线的「咨询宝贝」商品卡，消息按「头像 + 昵称 + 时间 + 气泡」排布，客服消息右对齐；底部为图标工具栏（表情 / 图片 / 订单卡 / 素材库 / 常见问题 / 话术拆分 ｜ 快捷短语 / 商品卡片 / 转交 / 结束会话）与 Enter 发送、Ctrl+Enter 换行。右栏为「订单 / 商品 / 快捷短语」三页签（咨询宝贝卡片 + 邀请下单、计算价格、规格属性、商品视频、商品评价动作按钮 + 订单状态页签）。
- **断线超时中止（方案 4.1 / 4.7 / 4.8）**：客服端曾连接实时通道、但超过 `disconnectGraceSec`（默认 60 秒）没有任何信号时，该客服进行中的会话按异常中止（0 分）计入并自动结束接待任务；只用 HTTP 调接口、从未建立实时连接的账号不会误判。
- **素材库按参考图对齐（方案 3.3.5 / 参考图 2、3）**：顶部「买家咨询背景 / 买家咨询内容」页签 + 筛选条（关键词、创建人、查询、重置）+ 左侧「模板分类」面板（新建分类、分类关键词、支持拖拽排序、分类下素材数量）+ 表格（背景：名称与需求、创建人、最后修改时间、操作；内容：模板名称含「官」徽标与售前/售后标签、买家咨询问题、图片、买家接受方案、创建人、最后修改时间、操作）。
- **新建聊天剧本弹窗按参考图对齐（参考图 4）**：分「基础设置 / 剧本信息 / 剧本内容」三段；支持创建模式（单个剧本走单条创建接口、批量剧本走交叉生成）、创建方式（自定义创建，根据聊天案例创建为二期）、剧本自动命名、接待类型、沟通风格、关联商品缩略图预览与背景/内容多选。
- **异步批量生成（方案 3.3 / 5.7 / 7.2）**：生成数量超过 `batchAsyncThreshold`（默认 100）时改为后台任务，`POST /api/scripts/batch-generate` 返回任务 ID；新增 `GET /api/scripts/batch-generate/tasks/:id`（进度）与 `POST .../cancel`（取消，已生成剧本保留）。前端以进度条展示并支持中途取消。
- **接口清单补齐（方案 7.2）**：新增 `POST /api/auth/refresh`（令牌续签，账号停用后拒绝续签）与 `PUT /api/groups/:id`（小组更新）。错误码与方案 7.4 表完全一致。
- **权限矩阵修正（方案 2.2）**：批注改为仅管理员/主管可新建（客服仅查看与回复），并给「回复批注」补上越权校验（此前按 id 直接更新、任意用户可改）；主管操作限制在本组范围。
- **情绪升级追问（方案 3.7.4 / 9.2 场景四）**：情绪值达到 `emotionEscalateThreshold`（默认 80）后，买家会在当轮追加一条升级追问（每轮只追加一次），而不是只标记一个内部状态。
- **导入分类校验（方案 9.2 场景七）**：商品导入时分类不在商品分类字典内会计入失败清单（行号 + 原因），与「重复商品 ID」「价格非法」一并满足导入异常验收场景。
- **默认聊天占比对齐（方案 10.3）**：内置五种风格恢复为方案默认的 30/15/20/20/15；扩充的三种风格（新手小白 / 精明比价 / 多疑较真）保留在风格库中，默认不参与分配，带教可在《沟通风格》页填写占比后启用。
- **下架商品不能进入新剧本（方案 9.1）**：新建剧本的商品下拉只列出上架商品，后端在批量生成/单条创建时也会校验，选中下架商品会明确报错。
- **为客服开放指定难度（方案 4.4）**：新增 `POST /api/accounts/:id/unlock-levels`（管理员/主管，主管限本组），账号页新增「开放难度」入口，可勾选 L1～L4 直接开放。
- **商品与剧本的关联统计改为精确匹配（方案 6.2 `script_count` / 9.1）**：`product_ids` 是 JSONB 数字数组，此前用 `LIKE '%id%'` 统计，会把 id=1 误算到 `[11]`、`[21]` 上，导致「关联剧本数」虚高、删除引用判断偏保守。现已统一改为数组包含匹配（`product_ids @> '[id]'`）并在前端列表用脚本侧精确统计。

## 六、内置内容库与二次创作

所有培训内容的唯一来源是 [`backend/src/db/seed-content.ts`](backend/src/db/seed-content.ts)：`npm run seed` 或内存模式启动时会自动同步进数据库，并按「背景 × 内容」交叉生成剧本。当前内置规模：

| 内容类型 | 数量 | 说明 |
| --- | --- | --- |
| 买家咨询背景（素材） | 32 | 使用场景、送礼对象、人群特征、购买经验、性格特征、关注点等画像 |
| 买家咨询内容 | 300 | 覆盖商品与服装专项、价格活动、物流快递、订单与账号、会员服务、退换货、售后反馈、质量与投诉升级、发票 |
| 商品 | 100 | 覆盖 13 个类目，供剧本关联 |
| 快捷短语 | 42 | 开场、商品、价格、物流、订单、售后、安抚、结束八类 |
| 沟通风格 | 8 | 占比合计 100%，决定批量生成剧本时的风格分布 |
| 生成剧本 | 900 | 每条内容生成 3 个剧本，**只关联服装类商品** |

剧本的生成规则由 [`backend/src/db/seed-content.ts`](backend/src/db/seed-content.ts) 的两个常量控制：

- `SCRIPT_SCOPE_CATEGORIES`（当前 `['女装', '男装']`）：剧本只关联这些类目的商品；要放开范围把类目名加进去即可（例如追加 `'鞋靴'`、`'箱包'`）。
- `SCRIPT_VARIANTS_PER_CONTENT`（当前 `3`）：每条咨询内容生成几个剧本。商品与买家背景都按序号轮转挑选，保证同一内容下的背景与商品不重复、各背景被用到的次数均衡。

因此剧本总数 = 咨询内容数 × `SCRIPT_VARIANTS_PER_CONTENT`，只随内容量线性增长，扩商品库不会让剧本数量失控。带教在界面上手动「新建剧本 / 批量生成」不受这两个常量的限制。

新增内容时有两个硬约束（`npm run content:check` 会强制校验）：

1. `question_list` 与 `key_points` 必须一一对应、长度相等；要点少一组，该轮就会退化成几乎无法命中的兜底要点。
2. 同一组要点是「同时命中」而不是备选，因此每组固定 2 个短词，并保证这两个词会同时出现在一句正常回复里——例如「这款偏大，建议选小一码」同时命中 `偏大` / `建议`。

要点判定采用「短词子串」口径（见 `backend/src/modules/reception/reception.service.ts` 的 `matchKeyPoints`）。归纳性说法（如「解决方案」「处理时效」）不会出现在客服的自然回复里，需要登记到 [`backend/src/domain/key-point-aliases.ts`](backend/src/domain/key-point-aliases.ts) 的同义词表。

剧本生成口径统一在 [`backend/src/domain/question-seq.ts`](backend/src/domain/question-seq.ts)：内置剧本与界面上「新建剧本 / 批量生成」共用同一套规则（按接待阶段补追问、支持需转接主管的问题、自动避开重复话术）。

改动内容或剧本规则后，建议按下面两条自检加回归：

```powershell
npm run content:check     # 静态检查内容库结构与字段约束（不需要服务）
npm run scripts:check     # 检查运行中服务的剧本规模与覆盖是否均匀（需要服务已启动）
```

## 七、数据库备份与恢复

方案 5.10 要求「每日自动备份 PostgreSQL（pg_dump + 保留 30 天）」，两种方式任选：

**方式一：随部署自动执行** —— `docker-compose.yml` 内置 `backup` 服务，每 24 小时执行一次 `pg_dump`，备份写入宿主机的 `./backups` 目录，并按 `BACKUP_KEEP`（默认 30）自动清理超出份数的旧文件。

**方式二：手工或接入外部定时任务**：

```powershell
# backend/.env 中需配置真实 DATABASE_URL，且 USE_PG_MEM=false
npm run backup:db                       # 生成一份备份并按保留份数清理旧文件
BACKUP_KEEP=7 npm run backup:db         # 临时调整保留份数

# 恢复（破坏性操作，必须显式确认）
$env:CONFIRM_RESTORE='yes'; npm run backup -w backend -- --restore <备份文件>
```

未配置 `DATABASE_URL` 或处于内存库模式时会明确报错并退出，不会产生空备份；恢复命令在未设置 `CONFIRM_RESTORE=yes` 时只打印待执行的 `pg_restore` 命令供复核。
